Conclusión

Fundamentos para los requerimientos del software · Requerimientos Básicos del Sistema

Los requerimientos son la base de todo proyecto de software: definen qué debe hacer el sistema y bajo qué restricciones operará. Una ingeniería de requerimientos descuidada produce software de baja calidad, costos mayores, mantenimiento difícil y retrasos; una bien hecha reduce errores desde el principio.1

Puntos clave aprendidos

🧱

Tres niveles de audiencia

Usuario, contractual (SRS) y diseño: cada nivel se escribe para un lector distinto.

⚙️

Funcionales y no funcionales

Los funcionales dicen qué hace el sistema; los no funcionales, cómo opera. Estos últimos deben ser medibles.

📐

Reglas de Heininger

Solo comportamiento externo, restricciones claras, fácil de cambiar, apoyo al mantenimiento, vida útil y respuesta a fallos.

✅

Cualidades de un buen requerimiento

Específico, claro, completo, consistente, verificable, priorizado y trazable.

🔄

Un ciclo de cinco etapas

Elicitación, análisis y negociación, especificación, validación y gestión de cambios.

🏗️

Requisitos críticos

Seguridad → capas; rendimiento → componentes grandes; disponibilidad → componentes redundantes.

Reflexión final

«Un requerimiento bien escrito debe ser específico, claro, completo, consistente, verificable, trazable y necesario. Si no se puede probar que se cumple, no es un buen requerimiento.»6 — Robertson y Robertson (2012), cap. 5, p. 112

Entender estas bases permite hablar el mismo idioma con clientes, analistas y programadores. Los requerimientos no son un documento que se escribe una vez y se archiva: evolucionan con el proyecto, y por eso conviene redactarlos de forma modular, verificable y fácil de actualizar para que el código y la especificación no se desincronicen.2 Esta habilidad será útil en cualquier proyecto de la carrera, desde una tarea integradora hasta un sistema real con cliente.
